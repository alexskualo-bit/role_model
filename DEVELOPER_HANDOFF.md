# Role Center: вход и создание ролевой системы

Документ для разработчика. Сайт сейчас является интерактивным прототипом: сохранение черновиков в браузере, подбор ролей по ключевым словам и передача запроса команде не являются производственными интеграциями.

## 1. Точка входа

1. Неавторизованный посетитель перенаправляется на вход ChatGPT. Не показывать ему рабочий стол, роли и данные клуба. Не создавать собственную форму пароля.
2. После подтверждённой платформой авторизации сервер получает стабильный `userId` и адрес электронной почты из доверенных заголовков. Пользователь с доступом к нескольким клубам выбирает клуб; права проверяются на сервере для каждого запроса.
3. Для пары `userId + clubId` прочитать `onboarding.status`. Если это новый пользователь данного клуба, показать **выбор пути** до рабочего стола. Если настройка уже начата, открывать последний незавершённый шаг. Если система запущена, открывать рабочий стол.
4. Два пути: `self_service` (самостоятельно) и `with_team` (совместно с командой). Выбор можно изменить до передачи запроса/запуска; изменение не должно удалять ответы фреймворка.

Рекомендуемые состояния: `new → path_chosen → framework_confirmed → designing_roles → owners_assigned → ready_for_launch → active`. Рабочий стол открывается сразу только при `active`; до `framework_confirmed` основные разделы недоступны. Не подменять состояние `active` одним фактом входа или выбора пути.

В прототипе первый вход и черновики сохраняются в localStorage по ключу с платформенным `userId`. Это отделяет демонстрационные данные разных авторизованных пользователей в одном браузере, но **не** является авторизацией, серверной изоляцией клубов или источником истины для многопользовательской системы. Старые неназначенные конкретному пользователю черновики прототипа намеренно не подхватываются автоматически.

## 2. Общий фреймворк — обязателен для обоих путей

Сохранить структурированные ответы: бизнес-задача клуба; целевая аудитория; ожидаемый измеримый результат; среда проявления роли; доступные источники данных; оператор ролей и его контакт; ресурс и горизонт пилота. Каждый пункт обязателен до перехода дальше. Хранить версию ответов, автора и время изменения. Отдельная роль может уточнять эти ответы, но не заменять клубный фреймворк.

### Самостоятельный путь

После сохранения фреймворка сервис подбирает 3–5 базовых ролей. Для каждой возвращает объяснение, какой задаче и аудитории она соответствует, и какие данные потребуются. Пользователь принимает/отклоняет предложение, может переименовать и адаптировать базовую роль или создать свою. Затем последовательно настраивает модель роли (назначение, критерии, шесть измерений индекса, эффекты участника и клуба, экономика, источники и цели), назначает владельца с именем, должностью и контактом, подключает данные и проверяет готовность пилота. Назначение участников не происходит автоматически без решения ответственного.

Кнопка «Подобрать следующую роль» доступна и после запуска. Новые рекомендации строятся по текущему фреймворку, уже существующему портфелю, задачам и подтверждённым данным; ранее выбранные роли исключаются или показываются как вариант пересмотра, а не дубликат. Рекомендация не создаёт роль без подтверждения оператора.

### Путь с командой

После того же фреймворка пользователь видит проверяемую сводку и отправляет запрос на проектирование. Требуется реальное серверное событие `role_design_request` со статусами `draft → submitted → in_progress → proposed → approved/revision_requested`. Указать получателя, автора, клуб, версию фреймворка, дату и историю решений. После предложения команды кнопка «Перейти к созданию ролей» открывает единый конструктор с проектами команды; далее те же настройки, владельцы, данные и пилот. Команда может запросить уточнение, не теряя черновик. В дальнейшем оператор может отдельно запросить у команды новую роль или адаптацию существующей.

## 3. Минимальная модель состояния

- `club_membership`: `userId`, `clubId`, права доступа.
- `onboarding`: `clubId`, `path`, `status`, `currentStep`, `updatedAt`.
- `framework`: `clubId`, `version`, ответы, `createdBy`, `updatedAt`.
- `role_design_request`: ссылка на версию фреймворка, статус, адресат, комментарии и история.
- `role`: базовый шаблон или кастомная, версия описания, статус жизненного цикла, пилот.
- `role_owner`: `roleId`, `userId` или приглашение, должность, контакт, период ответственности.
- `role_metric`: измерение, формула, вес, цель, период, источник, правило недостаточных данных.
- `role_recommendation`: входная версия данных, предложенная роль, обоснование, решение человека.

Разграничение: оператор видит портфель клуба и методологические настройки; владелец — свои роли, задачи, участников, эффекты и экономику. Проверки доступа нужны на API/сервере, а не только в интерфейсе.

## 4. Критерии готовности

1. Новый авторизованный пользователь не попадает на рабочий стол до выбора пути.
2. Оба пути приводят к одному и тому же обязательному фреймворку; пустые ответы блокируют переход.
3. Самостоятельный путь показывает объяснимые рекомендации, командный создаёт адресуемый запрос, а не только сообщение на экране.
4. После возвращения на сайт сохраняются путь, ответы и текущий шаг для конкретного клуба и пользователя.
5. После запуска оператор может запросить следующую роль через ИИ или команду, не проходя настройку заново.
6. Роль нельзя запустить без обязательных показателей и назначенного владельца; отсутствие данных не превращается в нулевой балл.

## 5. Что уже работает в прототипе

На опубликованном приватном Site доступ защищён входом ChatGPT. В приложении есть отдельный первый экран «авторизация подтверждена → выбор пути», общий фреймворк, оба сценария, конструктор и повторный подбор роли. Но localStorage, условный алгоритм подбора и экран подтверждения запроса нужны только для демонстрации. Для боевого продукта заменить их серверными записями, реальной интеграцией модели и доставкой запроса команде.
