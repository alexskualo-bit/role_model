# Role Center: проектирование и запуск ролевой системы

Документ для разработчика. Сайт сейчас является интерактивным прототипом: черновики сохраняются в браузере, подбор ролей по фреймворку демонстрационный. Внутри приложения нет регистрации профиля и отдельного пути с командой.

## 1. Точка входа

1. Неавторизованный посетитель перенаправляется на вход ChatGPT. Не показывать ему рабочий стол, роли и данные клуба. Не создавать собственную форму пароля.
2. После подтверждённой платформой авторизации сервер получает стабильный `userId` из доверенных заголовков. Отдельной анкеты регистрации в демо нет.
3. Для пары `userId + clubId` прочитать `onboarding.status`. Новому пользователю сразу показать фреймворк. Если настройка уже начата, открывать последний незавершённый шаг. Если система запущена, открывать рабочий стол.
4. В демо один самостоятельный сценарий. Консультацию с командой назначают вне приложения; отдельная ветка и форма обращения здесь не нужны.

Рекомендуемые состояния: `new → framework_confirmed → roles_designed → parameters_confirmed → owners_assigned → portfolio_distributed → ready_for_launch → active`. Рабочий стол открывается сразу только при `active`; до завершения настройки доступны только её шаги и необходимые экраны конструктора.

В прототипе первый вход и черновики сохраняются в localStorage по ключу с платформенным `userId`. Это отделяет демонстрационные данные разных авторизованных пользователей в одном браузере, но **не** является авторизацией, серверной изоляцией клубов или источником истины для многопользовательской системы. Старые неназначенные конкретному пользователю черновики прототипа намеренно не подхватываются автоматически.

## 2. Обязательный фреймворк

Сохранить структурированные ответы: бизнес-задача клуба; целевая аудитория; ожидаемый измеримый результат; среда проявления роли; доступные источники данных; ресурс и горизонт пилота. Каждый пункт обязателен до перехода дальше. Хранить версию ответов, автора и время изменения. Оператора и владельцев назначают **после** проектирования и подтверждения параметров ролей.

После сохранения фреймворка сервис подбирает 3–5 базовых ролей. Для каждой возвращает объяснение, какой задаче и аудитории она соответствует, и какие данные потребуются. Пользователь принимает/отклоняет предложение, может переименовать и адаптировать базовую роль или создать свою. Затем последовательно: (1) определяет и подтверждает параметры каждой роли — назначение, критерии, шесть измерений индекса, эффекты участника и клуба, экономику, источники и цели; (2) назначает оператора системы и владельца каждой роли с именем, должностью и контактом; (3) загружает/фиксирует первичный портфель ролей, распределяет роли по пилотам и проверяет нагрузку владельцев; (4) указывает источник данных и только затем запускает систему. Назначение участников не происходит автоматически без решения ответственного.

Кнопка «Подобрать следующую роль» доступна и после запуска. Новые рекомендации строятся по текущему фреймворку, уже существующему портфелю, задачам и подтверждённым данным; ранее выбранные роли исключаются или показываются как вариант пересмотра, а не дубликат. Рекомендация не создаёт роль без подтверждения оператора.

## 3. Минимальная модель состояния

- `club_membership`: `userId`, `clubId`, права доступа.
- `onboarding`: `clubId`, `status`, `currentStep`, `currentRoleId`, `updatedAt`. Возврат после перезагрузки должен открыть тот же шаг и ту же роль, если редактирование не завершено.
- `role_design_draft`: `clubId`, `roleId`, черновик индекса, эффектов и экономики, `updatedAt`; автосохранение не равнозначно подтверждению параметров.
- `framework`: `clubId`, `version`, ответы, `createdBy`, `updatedAt`.
- `operator_assignment`: статус `assigned/pending`, данные оператора при назначении; при `pending` подготовку можно продолжать, запуск блокируется.
- `role`: базовый шаблон или кастомная, версия описания, статус жизненного цикла, пилот.
- `role_owner`: `roleId`, `userId` или приглашение, должность, контакт, период ответственности.
- `role_metric`: измерение, формула, вес, цель, период, источник, правило недостаточных данных.
- `role_recommendation`: входная версия данных, предложенная роль, обоснование, решение человека.

Разграничение: оператор видит портфель клуба и методологические настройки; владелец — свои роли, задачи, участников, эффекты и экономику. Проверки доступа нужны на API/сервере, а не только в интерфейсе.

## 4. Критерии готовности

1. Новый авторизованный пользователь начинает с фреймворка, без анкеты профиля и выбора пути; до завершения настройки рабочий стол не открывается.
2. Пустые ответы фреймворка блокируют переход.
3. Подбор показывает объяснимые рекомендации по ответам фреймворка.
4. После возвращения на сайт сохраняются ответы, текущий шаг, редактируемая роль и её незавершённый черновик для конкретного клуба и пользователя.
5. При первичной настройке роли открываются внутри шага параметров: пользователь не уходит в другой раздел, а после сохранения возвращается к списку с отмеченным прогрессом. Создание своей роли также выполняется внутри шага проектирования.
6. Параметры ролей подтверждаются **до** назначения ответственных. При отсутствии оператора распределение доступно, но запуск блокируется; владелец с именем, должностью и контактом нужен для каждой роли.
7. Перед запуском видны состав первичного портфеля, пилот каждой роли и распределение по владельцам; портфель необходимо подтвердить.
8. После запуска оператор может запросить следующую роль через помощника, не проходя настройку заново.
9. Роль нельзя запустить без обязательных показателей и назначенного владельца; отсутствие данных не превращается в нулевой балл.

## 5. Что уже работает в прототипе

На опубликованном приватном Site доступ защищён входом ChatGPT. Само демо начинается с фреймворка и ведёт по одному самостоятельному маршруту: подбор, проектирование, параметры, ответственные, распределение, запуск. Регистрации профиля и командной ветки нет. На шаге ответственных объяснено различие оператора и владельца; можно отметить, что оператор пока не назначен, но запуск в таком случае блокируется. Текущий шаг и незавершённые поля сохраняются локально; после настройки роли пользователь возвращается к списку. До запуска другие разделы недоступны. В основном интерфейсе оставлена универсальная модель; материалы ClubFirst не удалены из исходных данных, но в демосценарии не показываются. Для боевого продукта заменить LocalStorage и условный подбор серверными записями и реальной интеграцией модели.
